# MicroChat wire protocol v1

This document describes the existing Android protocol implemented by the iOS
client. This is an experimental static-key protocol, not Signal or Double Ratchet.

## Public identities

`{ "enc": "…", "sign": "…" }` contains **unpadded base64url binary Tink
Keyset protobufs**, not raw public keys. Each keyset has one ENABLED, TINK-prefixed,
ASYMMETRIC_PUBLIC primary key. Other keyset types and key rotations are rejected
by this version. Private keysets never appear in profiles or invitations.

- Encryption type URL: `type.googleapis.com/google.crypto.tink.HpkePublicKey`.
- HPKE parameters use Tink enum values KEM=1, KDF=1, AEAD=2: X25519,
  HKDF-SHA256, AES-256-GCM. These protobuf values differ from RFC suite IDs.
- Signing type URL: `type.googleapis.com/google.crypto.tink.Ed25519PublicKey`.
- Each raw public key has 32 bytes. Proto version zero is omitted when encoding.
- TINK output prefix: `0x01 || uint32_big_endian(key_id)`.
- Fingerprint: lowercase hex SHA-256 of UTF-8 `enc + "\n" + sign`, preserving
  the exact serialized public-keyset strings from the invitation.

## Envelope

JSON fields are `v` (1), `sender`, `recipient`, `id`, `created`, `ciphertext`,
`signature`. `created` is a nonnegative integer number of Unix milliseconds.
UIDs match `[A-Za-z0-9_-]{10,128}`, IDs match `[A-Za-z0-9_-]{16,64}`.

The signed header is UTF-8, with no trailing newline:

```text
MicroChat-v1|<id>|<sender>|<recipient>|<created>
```

A new RFC 9180 **base-mode HPKE context** is created for every envelope using
DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM. Header bytes are the HPKE
`info` input; the AEAD associated-data input is **empty**. The context encrypts
one UTF-8 plaintext message at sequence number zero.

Decoded ciphertext:

```text
recipient_TINK_prefix[5] || encapsulated_X25519_key[32] || AES_GCM_ciphertext_and_tag
```

Decoded signature:

```text
sender_signing_TINK_prefix[5] || Ed25519(header || full_decoded_ciphertext)[64]
```

Both fields use unpadded base64url. Receivers validate IDs, key prefixes and
signature before HPKE decryption. iOS requires valid UTF-8 and no more than
12,000 plaintext bytes. Signatures must be exactly 69 bytes; decoded ciphertext
must be between 53 and 20,000 bytes. No plaintext is included in the relay body.

## Invitations and delivery

An invitation is `microchat:` followed by unpadded base64url UTF-8 JSON:

```json
{"v":1,"uid":"…","keys":{"enc":"…","sign":"…"},"databaseUrl":"https://…","apiKey":"…","name":"…"}
```

Recipients must obtain invitations through a trusted channel and compare key
fingerprints. The bundled client connects only to its shared Firebase database;
an invitation cannot replace the service configuration or pinned contact keys.

REST endpoints use anonymous Firebase Authentication and standard TLS validation:

- `/profiles/<uid>`: create-once public key bundle; authenticated exact-UID reads.
- `/peers/<ownUID>/<peerUID>`: owner grants `{ "allowed": true }`.
- `/queue/<recipient>/<sender>/<id>`: signed encrypted envelope.

The sender persists the complete outgoing envelope and local history in one
authenticated encrypted file before upload. Retries PUT the same envelope/ID.
The recipient checks the pinned sender key, authenticates and decrypts, commits
encrypted local history, then DELETEs the queue item. Retrying after a failed
DELETE does not add the same ID twice. Server acceptance is shown as "sent";
it is not a read receipt or proof of device delivery.

The sender cannot read the recipient queue. Both users must add each other's
invitations before delivery is authorized. The server sees routing metadata and
ciphertexts, and deletion does not guarantee removal of provider backups.

## Test fixtures

`Tests/Fixtures/android-v1.json` contains deliberately public test-only private
material generated by Android Tink. It is bundled only into tests, never the app.
`tests/IOSInteropTest.java` generates the Android envelope and verifies an actual
Swift-generated reply. Swift tests also verify exact public keyset serialization.
The tests do not use production accounts or change Firebase rules.
